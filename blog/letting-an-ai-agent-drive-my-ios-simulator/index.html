Letting an AI agent drive my iOS simulator, without handing it my Mac

I write PaisoLog on a Linux machine. The iOS simulator only runs on macOS. Here's how my AI coding agent now checks its own changes on a Mac across the room, and why its SSH key can do almost nothing else.

The problem

PaisoLog is a React Native (Expo) app. On Android, testing from Linux is easy: an emulator runs right here, and the agent can install, tap and screenshot it.

My agent is Claude Code, which writes a good part of PaisoLog these days. Nothing below depends on it, though: any agent that can run shell commands and use MCP tools can do the same.

iOS is the awkward one. The simulator ships with Xcode, Xcode only runs on macOS, and there's no Linux equivalent. I have a Mac on the same Wi-Fi, so the question became: can the agent on Linux drive the simulator on the Mac?

It can. None of the pieces are new, but putting them together took a few steps.

Linux                           Mac
agent ─── SSH ────────────────► MCP server → simctl/idb → Simulator
Metro ◄── tunnel :8081 ──────── PaisoLog (debug build)

1. Driving the simulator over SSH

Apple's xcrun simctl boots simulators, launches apps and takes screenshots, but it can't tap or type. For that I used idb, which can also list every element on screen with its label and position, so the agent taps "Add transaction" by name instead of guessing pixels.

Claude Code, like most coding agents, talks to tools over MCP, and there's already an open-source MCP server for the simulator, ios-simulator-mcp. MCP servers usually speak over stdin and stdout, and SSH carries those across the network unchanged. So the whole connection is one entry in the project's MCP config:

{
  "mcpServers": {
    "ios-sim": { "command": "ssh", "args": ["mac", "sim-mcp"] }
  }
}

No port to open, and SSH keys handle authentication. (sim-mcp will make sense in section 4.)

2. Getting my code onto the Mac without copying it

The code lives on Linux, and I didn't want to sync it to the Mac every time something changed. React Native apps load their JavaScript from a bundler called Metro, so Metro can run on Linux. The catch: the debug build installed on the simulator looks for Metro at localhost:8081 on the Mac.

Android developers already know the fix. adb reverse tcp:8081 tcp:8081 makes the phone's localhost:8081 point at your computer. SSH can do the same for the Mac:

ssh -N -R 8081:localhost:8081 mac

Now the Mac's localhost:8081 is Metro on Linux. Edit a file here, relaunch the app there, and it runs the new code.

3. One command to start, one to stop

Starting Metro, opening the tunnel, booting the right simulator and relaunching the app is four steps, so it became one script. Every step is skipped if it's already done, so it's safe to rerun after each change:

$ scripts/ios-remote.sh
✅ Metro already running on :8081
🔌 Opening reverse tunnel to mac...
📱 Booting simulator ...
🔄 Relaunching com.umangarora.paisolog...
✨ Launched. The first bundle takes ~20s.

$ scripts/ios-remote.sh stop-tunnel
🔌 Tunnel stopped
📴 Simulator ... shut down

Two details mattered more than I expected:

  • The tunnel blocks the Mac. While it's open it holds port 8081 on the Mac, so Metro can't start there when I sit down to work on the Mac itself. The agent closes the tunnel after every test, and a Claude Code hook closes it when the session ends, in case it forgets.
  • Clean up only what you started. The script remembers whether it booted the simulator. If it did, stopping shuts it down again; if I'd already booted it on the Mac, it's left alone. It also refuses to run if something other than the tunnel holds the Mac's port 8081, because then the app would quietly load the Mac's copy of the code instead.

4. Taking most of the access back

At this point everything worked, and the agent had a full shell on my Mac. That's more than it needs: my files, my browser profiles, anything my user can touch. If the Linux machine were ever compromised, so would the Mac be.

OpenSSH has had a fix for this for decades, and you've probably used it without noticing. When you git push to GitHub over SSH, your key doesn't get a shell; it gets a program that only speaks git. That's a forced command in ~/.ssh/authorized_keys:

restrict,port-forwarding,permitlisten="localhost:8081",permitopen="localhost:9",command="/Users/you/bin/paisolog-gate" ssh-ed25519 AAAA...
  • restrict turns off everything: shells, terminals, agent and port forwarding.
  • port-forwarding with permitlisten allows exactly one reverse tunnel, on localhost:8081. permitopen points local forwards at a port nothing listens on, so they're useless.
  • command means whatever the key asks to run, the Mac runs the gate script instead and hands it the request.

The gate is a short bash script with a fixed list of verbs, and anything else is refused. Trimmed down:

CMD="${SSH_ORIGINAL_COMMAND:-}"
echo "$(date '+%F %T') ${CMD:0:300}" >> "$LOG"
VERB="${CMD%% *}"

case "$VERB" in
  sim-mcp)      exec npx -y "ios-simulator-mcp@2.1.0" ;;
  metro-status) curl -s -m 3 "localhost:8081/status" ;;
  booted)       xcrun simctl list devices booted | grep -oE "$UDID_PATTERN" ;;
  boot)         U=$(udid_arg); xcrun simctl boot "$U" && xcrun simctl bootstatus "$U" ;;
  launch)       U=$(udid_arg); xcrun simctl launch "$U" "$BUNDLE_ID" ;;
  screenshot)   ... ;;   # PNG on stdout
  db-query)     ... ;;   # read-only SQL, see below
  *)            deny "'${VERB:-<interactive shell>}' is not allowed" ;;
esac

A few choices in there:

  • Arguments are checked. Simulator IDs must match the UUID format, so boot ../../etc goes nowhere.
  • The app's database is read-only. db-query opens it with sqlite3 -safe -readonly, which blocks writes, ATTACH and sqlite's own .shell command. Dot-commands are refused outright.
  • The MCP server is pinned. npx -y ios-simulator-mcp would run whatever version npm has today. Pinning it means a new release can't change what runs on my Mac without me noticing.
  • Every call is logged on the Mac.
  • The gate can't change itself. Updating it means copying a new version on the Mac by hand, which is the point.

Claude wrote the gate and then tested it by trying to get past it, using a throwaway key first so a mistake couldn't lock me out. This is what the agent's key gets now:

$ ssh mac id
paisolog-gate: 'id' is not allowed
$ ssh mac 'booted; id'
paisolog-gate: 'booted;' is not allowed
$ ssh mac
paisolog-gate: '<interactive shell>' is not allowed
$ scp mac:.zshrc .
scp: Connection closed
$ ssh -N -R 2222:localhost:22 mac
Error: remote port forwarding failed for listen port 2222
$ ssh mac "db-query ATTACH '/tmp/x.db' AS x;"
line 0: cannot run ATTACH in safe mode

Meanwhile launching the app, screenshots, read-only queries and the MCP server all still work.

5. Closing the other door

The gate only covers that one key. With Remote Login turned on, the Mac also accepted passwords over SSH, from any device on the network. Two lines turn that off:

printf 'PasswordAuthentication no\nKbdInteractiveAuthentication no\n' | sudo tee /etc/ssh/sshd_config.d/100-keys-only.conf
sudo launchctl kickstart -k system/com.openssh.sshd
$ ssh -o PubkeyAuthentication=no mac
you@mac: Permission denied (publickey).

Last, I reserved both machines' IP addresses on the router, so the setup survives a reboot. One catch: macOS gives each Wi-Fi network a "private" MAC address, which can rotate. Set it to Fixed for your home network, or the reservation stops matching.

Things the agent tripped over

  • Fast typing drops keys. idb sends a whole string in one burst. In PaisoLog's search, the first letter starts work on ~28,000 transactions, and the remaining keystrokes vanished: "fuel" came out as "F". Typing one character at a time works.
  • The first letter gets capitalised, like on a real iPhone. Worth remembering before you assert on text.
  • Edge swipes don't go back. A swipe from the screen's edge didn't trigger the iOS back gesture; tapping the back button did.
  • Know which build you have. My simulator had a plain debug build, not an Expo development client, so dev-client links did nothing. That's why the tunnel exists at all.

Is any of this new?

Not really. Teams have shared Macs for iOS work for years, adb reverse is the same trick as the tunnel, forced commands are how Git hosts work, and key-only SSH is the first thing anyone does to a server. Open-source tools already let AI agents drive the simulator.

What felt worth writing down is the combination. It's tempting to hand an agent a shell and move on. A shell is the easy path, but an agent only needs a short list of verbs, and an afternoon of setup buys that. Next time it runs a command on my Mac, I know exactly which ones it can be.
